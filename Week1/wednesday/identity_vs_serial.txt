================================================================================

        IDENTITY  vs  SERIAL  —  why the PK is GENERATED ALWAYS AS IDENTITY

            use   ->  id bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY
            avoid ->  id bigserial

        Written after the savepoint / aborted-transaction exercise on
        sandbox.users   (Week 1 - Wednesday)

================================================================================


--------------------------------------------------------------------------------
  0 - CONTEXT FROM THE EXERCISE
--------------------------------------------------------------------------------

  * Inserted rows -> BEGIN -> SAVEPOINT -> did work -> rolled back to the
    savepoint -> carried on -> COMMIT.

  * The surviving ids had a GAP. That gap is the whole point:

        +----------------------------------------------------------------+
        |  The sequence behind the column is NON-TRANSACTIONAL.          |
        |  Once nextval() hands out a number it is spent.                |
        |  ROLLBACK - whole txn or to a savepoint - never returns it.    |
        +----------------------------------------------------------------+

  * So the id is not a row counter and never was. It is an opaque,
    system-owned surrogate key whose only job is to be unique.

  * serial and identity behave IDENTICALLY here - both leak values on
    rollback. The gap is not the reason to prefer identity; it just makes
    clear what kind of thing the column is, which shapes which declaration
    is the honest one.


--------------------------------------------------------------------------------
  1 - THE REAL REASONS TO USE  GENERATED ALWAYS AS IDENTITY
--------------------------------------------------------------------------------

  1.1  serial is not a type, it is a macro
  .............................................................................
       Writing  id serial  quietly expands to FOUR things:

           1. an int4 column
           2. a sequence object
           3. column DEFAULT nextval('<that sequence>')
           4. an OWNED BY link from sequence -> column

       Glued together by convention. IDENTITY is ONE real property of the
       column, tracked in the catalog as a single thing.
       -> less to fall out of sync, cleaner dump/restore, cleaner to drop


  1.2  GENERATED ALWAYS actually protects the key
  .............................................................................
       With serial, the DEFAULT only fires when you OMIT the column.
       Nothing stops:

           INSERT INTO users (id, email) VALUES (50, 'x@y.com');   -- accepted

       The row lands, the sequence is untouched, and later auto inserts climb
       1, 2, 3 ... 49, 50  ->  BOOM: duplicate key - surfacing much later,
       nowhere near the INSERT that caused it.

       GENERATED ALWAYS rejects any caller-supplied value outright. You must
       opt in, on purpose, with:

           INSERT INTO users (id, ...) OVERRIDING SYSTEM VALUE VALUES (50, ...);

       After an exercise built around deliberately creating gaps, this
       matters: nobody gets to "tidy up" a gap by inserting an explicit id
       and planting a landmine.

       Note - GENERATED BY DEFAULT AS IDENTITY also exists: a proper identity
              column but as permissive as serial. ALWAYS is the stricter,
              safer default.


  1.3  It is the SQL standard
  .............................................................................
       IDENTITY is standard SQL, portable across engines. serial is a
       Postgres-ism kept for backward compatibility. Learn the standard form.


  1.4  Fewer privilege / ownership footguns
  .............................................................................
       serial   -> caller may also need  GRANT USAGE ON SEQUENCE ...
                   the sequence can be orphaned if objects are altered
                   carelessly.
       identity -> only INSERT on the table is needed; the sequence is
                   managed as part of the column:
                       ALTER TABLE ... ALTER COLUMN id RESTART WITH ...
                       ALTER TABLE ... ALTER COLUMN id SET GENERATED ...
                   and it is dropped automatically with the column.


  1.5  bigint from the start
  .............................................................................
       Wrote bigint, not int.
           serial   = 32-bit
           bigint identity / bigserial = 64-bit
       Gaps are normal and burn the range faster than row count suggests, so
       an 8-byte key is the safe default for anything that might grow.


--------------------------------------------------------------------------------
  2 - COMMON MISCONCEPTIONS  (caught while studying this)
--------------------------------------------------------------------------------

  MYTH  "IDENTITY keeps the counter gapless, serial doesn't."
  FACT  BOTH gap. Both sit on a non-transactional sequence. Rollbacks,
        aborted txns, constraint failures, the CACHE setting and crashes all
        burn numbers under either declaration. Need a true 1..N? Compute
        row_number() at read time - don't expect it from the id.

  MYTH  "users and orders might share a sequence / share id 5."
  FACT  Every serial/identity column gets its OWN dedicated sequence
        (users -> users_id_seq, orders -> orders_id_seq). Independent
        counters. orders.id climbing has zero effect on users.id. A user row
        with id 5 and an order row with id 5 are unrelated - the link between
        them is a FOREIGN KEY (orders.user_id -> users.id), never a shared
        counter.


--------------------------------------------------------------------------------
  3 - QUICK COMPARISON
--------------------------------------------------------------------------------

    aspect                | bigserial                 | GENERATED ALWAYS IDENTITY
    ----------------------+---------------------------+--------------------------
    SQL standard          | no (Postgres macro)       | yes
    catalog objects       | column + sequence + ...   | one column property
    manual id insert      | silently allowed          | blocked unless
                          | (de-syncs sequence)       | OVERRIDING SYSTEM VALUE
    privileges to insert  | INSERT + USAGE on seq     | INSERT on table only
    width                 | 64-bit (serial = 32)      | whatever you declare
    gapless?              | NO                        | NO (same as serial)


--------------------------------------------------------------------------------
  4 - ONE-LINE VERSION
--------------------------------------------------------------------------------

  serial is old syntactic sugar: the key stays writable and the sequence
  hangs off the side as a loosely attached object.

  GENERATED ALWAYS AS IDENTITY is the standard, single-object way to say
  "this column is a system-controlled surrogate key that callers must not
  set" - exactly what a primary key that legitimately has gaps should be.
